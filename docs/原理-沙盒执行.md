# 原理：沙盒执行（Sandboxed Execution）

> 状态：v0.1（设计期，落地前以本文为准绳）
> 配套：架构文档.md §6（安全模型）/ 需求文档 FR-8 FR-3.4 / 索引文档.md
> 本文回答：模型要跑 `bash` 命令时，dscode 怎么在"让它干成事"和"别把机器搞坏"之间划线——子进程、权限、超时、信号、路径保护、以及后续系统级沙箱。

---

## 0. TL;DR

**Agent 手里有 `bash` 工具，就等于把命令行交了出去。沙盒执行的目标是：让命令在受控的子进程里跑，超时能中断、危险命令被拦、逃逸路径被拒、输出被截断——而不牺牲"命令真的能跑成"的能力。**

核心机制：
1. **子进程隔离**：bash 工具在 cwd 的子进程执行，非 dscode 主进程内联跑。
2. **超时 + 信号**：超时后发信号中断，防 `sleep 100` 这类命令挂死 loop。
3. **输出截断**：stdout/stderr 截断（50KB 级），防海量输出撑爆 context。
4. **权限网关前置**：危险命令（`rm -rf`、`sudo`、`git push --force`）在 execute 前被识别并二次确认 / deny。
5. **路径白名单**：`..` 逃逸、敏感路径（`.env`、`secrets/`）被 deny。
6. **后续演进**：系统级沙箱（landlock / seatbelt）留作 v1.x，本期靠"子进程 + 权限 + 路径"兜底。

---

## 1. 为什么需要沙盒执行

### 1.1 问题

`bash` 工具是 Agent 能力最强的工具，也是风险最大的：
- **挂死**：`sleep 100`、`read`、交互命令把 loop 卡住。
- **破坏**：`rm -rf`、`sudo`、`git push --force` 不可逆。
- **逃逸**：`cd ..`、访问 `~/.ssh`、写 `.env` 越出工作目录与敏感区。
- **污染**：命令输出几 MB，全部回传撑爆 context、拖慢模型。

### 1.2 解法：多层而不是一层

单一沙箱（无论多强）都会"要么太松出事、要么太紧干不成事"。dscode 用**分层**：命令级匹配（权限规则）→ 进程级控制（子进程/超时/信号）→ 路径级保护（白名单）→ 未来的系统级隔离。每一层独立失败也能单独兜住一大类风险。

## 2. 子进程隔离

### 2.1 为什么是子进程

- 命令在**独立进程**跑，dscode 主进程不因命令崩溃而崩溃。
- 可通过 `pid` 精确 kill / 发信号，不影响主进程。
- 可设 `cwd`（默认工作目录）、env、stdio 管道。

### 2.2 执行模型

```ts
// 伪代码
const { spawn } = await import("node:child_process");
const child = spawn("bash", ["-c", command], {
  cwd, env: sanitizedEnv, stdio: ["pipe", "pipe", "pipe"],
});
// 收集 stdout/stderr，超时后 child.kill("SIGTERM") → SIGKILL
```

- 命令经 `bash -c` 执行，保留 shell 语义（管道、重定向、变量）。
- 不直接拼接进 `sh -c` 而是 spawn 数组传参，避免注入层。
- 输出累计到 50KB 上限即截断并标记 `truncated`。

---

## 3. 超时与信号

### 3.1 超时

- 每个 bash 调用携带 `timeout`（默认有限，如 30s；不得无限）。
- 超时 → 先 `SIGTERM` 优雅中断，宽限期后再 `SIGKILL` 强制。
- 验收：`bash sleep 100` 配 `timeout: 1` 能被中断（对应 todos M1-S3 bash 验收）。

### 3.2 信号与退出码

- 记录退出码（`code`）与 signal（`signal`），回传模型以判断成败。
- 模型可据此自愈（命令失败 → 换法重试，见 原理-plan-and-execute.md §9）。

---

## 4. 权限网关前置

bash 工具不是"命令直接跑"，而是**先过权限网关**（架构文档 §6、需求 FR-8）：

- **四级审批模式**：`read-only` / `ask`（默认）/ `auto-edit` / `full-auto`。
- **危险命令识别**：`rm -rf`、`sudo`、`git push --force`、`dd`、`mkfs` 等，无论模式几乎都二次确认（除非 full-auto + allow 规则）。
- **allow/deny/ask 规则**：glob + 命令前缀匹配，如 deny `rm -rf`、ask `git push`。
- **read-only 模式**：写操作/bash 写命令被 deny（对应 Plan 模式）。

> 关键：**权限在前，执行在后**。命令在 spawn 之前就先被规则判定，不是跑起来再拦。

---

## 5. 路径保护

- **路径规范化**：解析 `..`、符号链接，拒绝逃逸出 cwd / 工作目录的路径。
- **敏感路径 deny**：`.env`、`secrets/`、`.ssh/`、`node_modules/` 等默认 deny（读/写/删均适用，见 原理-file-tools.md §7）。
- 需要读写白名单外路径 → 显式配置 allow 规则。

---

## 6. 系统级沙箱（v1.x 演进）

架构文档 §6 明确：**v1 不做系统级沙箱**（landlock / seatbelt），靠"子进程 + 权限 + 路径"兜底。开放问题（架构文档 §10）决策后转 v1.x：

| 方案 | 平台 | 能力 |
|------|------|------|
| landlock | Linux | 进程级文件访问限制（无权限降级） |
| seatbelt | macOS | 进程级系统调用 / 文件访问限制 |
| Windows 对应 | Windows | 需评估（AppContainer / 受限 token） |

演进方向：把"路径白名单"从 dscode 内部校验下沉到 OS 强制，减少"规则漏了"的依赖。

---

## 7. 抓手与判据

| 抓手 | 判据 |
|------|------|
| 超时可控 | `sleep 100` 配 timeout:1 被中断，主进程不挂 |
| 危险命令拦截 | `rm -rf`/`sudo`/`git push --force` 在 ask 模式 100% 先确认 |
| 输出截断 | 单次输出 >50KB 被截断并标记 truncated，不撑爆 context |
| 路径不逃逸 | `..` 逃逸 / 敏感路径访问 100% 被拒 |
| 子进程隔离 | 命令崩溃不改写主进程，退出码/signal 正确回传 |

---

## 8. 反模式（明确不做）

- ❌ "命令在主进程内联跑"——崩溃即全崩。
- ❌ "bash 无限超时"——必挂死 loop。
- ❌ "权限在执行后拦截"——必须前置，跑起来就晚了。
- ❌ "输出全量回传"——必截断。
- ❌ "假装系统级沙箱已落地"——v1 是子进程+权限+路径，沙箱是 v1.x。
